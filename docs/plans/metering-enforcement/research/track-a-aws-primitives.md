## VERIFIED

### 1. Application Inference Profiles (AIPs) — NEGATIVE for our path

- What they are: user-created Bedrock resources that reference one model (or a cross-region profile); you put the **profile ARN in place of the model ID** in `InvokeModel`/`Converse` calls; cost-allocation tags on the profile attach to the billing record of every request. [DOC] https://docs.aws.amazon.com/bedrock/latest/userguide/cost-mgmt-application-inference-profiles.html (retrieved 2026-07-14): "Application inference profiles (AIPs) let you attribute Amazon Bedrock costs ... for the Amazon Bedrock InvokeModel and Converse APIs **on the `bedrock-runtime` endpoint**. ... **For workloads using Responses and Chat Completions on the `bedrock-mantle` endpoint, use Projects instead.**"
- Granularity: "AIPs deliver aggregated billed dollars to AWS Cost Explorer and CUR (classic CUR and CUR 2.0). **The finest grain is per usage type per day; they do not produce per-request cost.**" (same page)
- Our path: **does NOT apply.** The mantle endpoint takes plain model-ID strings (`anthropic.claude-opus-4-7`, `qwen.qwen3-32b`); the gateway inference target's `ModelEntry` schema is a single `model` string/glob (pattern `[a-zA-Z0-9\-\._\*\?@]+(...)`) — an `arn:aws:bedrock:...:inference-profile/...` ARN does not fit this model-routing scheme and AWS's own docs direct mantle users to Projects instead. [DOC] https://docs.aws.amazon.com/bedrock-agentcore-control/latest/APIReference/API_ModelEntry.html (retrieved 2026-07-14).
- Nuance: the Projects-vs-Inference-Profiles comparison table lists Chat Completions on **bedrock-runtime** as supported by inference profiles ("Supported APIs ... Native Bedrock APIs (Invoke, Converse), OpenAI-compatible API (Chat Completions)"; endpoint `bedrock-runtime.{region}.amazonaws.com`). So AIPs could only re-enter the picture if we re-pointed a provider target at bedrock-runtime — a different endpoint from our live connector. [DOC] https://docs.aws.amazon.com/bedrock/latest/userguide/projects.html (retrieved 2026-07-14).
- [LIVE] `aws bedrock list-inference-profiles --type-equals APPLICATION --region us-east-1` → `{"inferenceProfileSummaries": []}` — none exist in the account today.

### 1b. Bedrock **Projects** — the mantle-native replacement (POSITIVE, big finding)

- [DOC] https://docs.aws.amazon.com/bedrock/latest/userguide/projects.html (retrieved 2026-07-14): "Projects can only be used with models that use the OpenAI-compatible APIs against the bedrock-mantle endpoint." A Project is a logical workload boundary with: OpenAI-compatible management API (`POST/GET $BASE/organization/projects`, update/archive), AWS tags on the project, an ARN (`arn:aws:bedrock-mantle:{region}:{acct}:project/proj_...`), up to **1000 projects/account**. Every account has a **default project**; "Requests that don't specify a project ID are associated with the default project" — matching our observed `Project="default"` metrics dimension.
- Per-request association: HTTP header **`OpenAI-Project: proj_...`** (or OpenAI SDK `project=` param). Documented for Responses and Chat Completions. [DOC] projects.html + https://docs.aws.amazon.com/bedrock/latest/userguide/cost-mgmt-projects.html (retrieved 2026-07-14).
- Cost attribution: "When you associate an inference request with a project, the project's tags are attached to the billing record for that request." Tags flow to Cost Explorer and **CUR 2.0** after cost-allocation-tag activation (up to 24h, not retroactive). Finest grain: per usage type per day. And explicitly: "**Per-request metadata tagging is not available on the `bedrock-mantle` endpoint, so per-prompt cost detail is not currently available for Amazon Bedrock mantle workloads.**" [DOC] cost-mgmt-projects.html.
- IAM enforcement hook: project ARN is an IAM resource; actions `bedrock-mantle:CreateInference`, `GetProject`, `ListProjects`, `CreateProject`, etc. Example doc policy allows `bedrock-mantle:CreateInference` on a specific `project/proj_abc123` — i.e., you can **allow/deny inference per project** on the calling principal (for us: the gateway's execution role). [DOC] https://docs.aws.amazon.com/bedrock/latest/userguide/security-iam-projects.html (retrieved 2026-07-14).
- Responses API state is **scoped by Project** ("A response from one Project cannot be used as the previous response or read in a second Project"; stored 30 days unless `store:false`). [DOC] https://docs.aws.amazon.com/bedrock/latest/userguide/bedrock-mantle.html (retrieved 2026-07-14).
- Reaches our path? The header must traverse the AgentCore gateway. Two documented mechanisms exist to do that (neither exercised yet — see UNVERIFIED): gateway target `metadataConfiguration.allowedRequestHeaders` (header propagation to target) [DOC] https://docs.aws.amazon.com/bedrock-agentcore-control/latest/APIReference/API_CreateGatewayTarget.html (retrieved 2026-07-14), and REQUEST-interceptor header injection via `transformedGatewayRequest.headers` for HTTP/inference targets [DOC] https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-interceptors-types.html (retrieved 2026-07-14).

### 2. Bedrock model-invocation logging — NEGATIVE for mantle

- [DOC] https://docs.aws.amazon.com/bedrock/latest/userguide/model-invocation-logging.html (retrieved 2026-07-14): loggable operations are Converse/ConverseStream/InvokeModel/InvokeModelWithResponseStream, and explicitly: "**Model invocation logging is only supported for calls made through the `bedrock-runtime` endpoint. Calls made through other endpoints, such as the Responses API on the `bedrock-mantle` endpoint, are not currently captured by invocation logging.**"
- [LIVE] `aws bedrock get-model-invocation-logging-configuration --region us-east-1` → empty (not even enabled in-account; moot for mantle anyway).
- The mantle-side audit substitute is **CloudTrail data events**: [DOC] https://docs.aws.amazon.com/bedrock/latest/userguide/logging-cloudtrail-mantle.html (retrieved 2026-07-14). `eventSource: bedrock-mantle.amazonaws.com`; inference (`CreateInference` for POST /v1/responses, /v1/chat/completions, /v1/embeddings, **POST /anthropic/v1/messages**, CountTokens) is a **data event** (must be enabled via advanced event selectors on resource types `AWS::BedrockMantle::Project|CustomizedModel|Reservation`; extra CloudTrail data-event charges). Captured request params include `model`, `stream`, `service_tier`, `metadata` (chat/completions + responses), `max_tokens` (messages); customer `metadata` is "logged verbatim". The event `resources[]` carries the **project ARN**. `responseElements: null` — **no token counts in CloudTrail**. Contrast noted in doc: on bedrock-runtime, inference is a free management event; "CloudTrail Lake queries ... that filter on bedrock.amazonaws.com or bedrock-runtime.amazonaws.com will not capture bedrock-mantle activity."

### 3. CloudWatch metrics — `AWS/BedrockMantle` IS documented (no longer a mystery)

- [DOC] https://docs.aws.amazon.com/bedrock/latest/userguide/monitoring-mantle-metrics.html (retrieved 2026-07-14) — dedicated page: "The Amazon Bedrock OpenAI-compatible endpoint publishes customer-facing metrics to CloudWatch under the **`AWS/BedrockMantle`** namespace." Covers Responses + Chat Completions + **Anthropic Messages** traffic on the mantle endpoint (bedrock-runtime traffic goes to `AWS/Bedrock` instead).
  - Metrics: `Inferences`, `InferenceClientErrors` (4xx), `TotalInputTokens`, `TotalOutputTokens` (aggregate billable tokens per publish interval), and `InputTokens`/`OutputTokens` (**one datum per inference**, published at Project+Model level only — usable for p50/p90/p99 per-request token stats).
  - Dimensions: **`Project`** (project ID) and `Model`; four granularity levels (Account, Project, Model, Project+Model). "Project+Model level — primary level for cost analysis."
  - Explicit deltas from bedrock-runtime metrics: separate namespace; renamed metrics (`Inferences` vs `Invocations`, `TotalInputTokens` vs `InputTokenCount`); **`Project` dimension exists only on mantle**; in-region only (no CRIS aggregation); **no latency/TTFT metrics yet**.
- [LIVE] `aws cloudwatch list-metrics --namespace AWS/BedrockMantle --region us-east-1` → 32 metric series: `Inferences`, `InferenceClientErrors`, `TotalInputTokens`, `TotalOutputTokens`, `InputTokens`, `OutputTokens`; dimensions `Model` ∈ {`openai.gpt-5.4`, `openai.gpt-5.5`, `anthropic.claude-fable-5`} and `Project="default"` — exactly matching the doc model, and confirming all our current traffic lands in the default project.
- [LIVE] namespace census: `AWS/Bedrock` (265 series), `AWS/BedrockMantle` (32), `AWS/Bedrock-AgentCore` (5801), custom `bedrock-agentcore` (36090).
- "Is there a projects feature? per-request project header?" — **Yes**: Projects API + `OpenAI-Project` header (see 1b). The `Project` metric dimension is the project ID.

### 4. bedrock-mantle service quotas — account-level per-model TPM backstop (CONFIRMED)

- [DOC] https://docs.aws.amazon.com/bedrock/latest/userguide/quotas-mantle.html (retrieved 2026-07-14):
  - Two quota types per model per region: "Bedrock Mantle **input tokens per minute** for {model}" and "**output tokens per minute** for {model}", "Shared across all APIs served by the endpoint for that model" (chat completions + Responses + Messages combined).
  - "**The `bedrock-mantle` endpoint does not enforce requests-per-minute (RPM) quotas.** Throttling is governed solely by the input and output token quotas."
  - Admission algorithm: input tokens + `max_tokens` (or model max if unset) reserved against input TPM → HTTP 429 if it would exceed; output tokens counted during generation, and **generation stops mid-stream with a cutoff finish reason if output TPM is hit**; unused reservation replenished after completion. Cached prompt-cache reads don't count against input TPM. Internal rate limiting beyond published quotas may apply.
  - Separate from bedrock-runtime quotas ("separate quota allocations, even when calling the same underlying model"); custom inference-profile / batch / Provisioned Throughput quotas do not exist on mantle.
  - Increases: visible in Service Quotas but "quota increase requests are not currently processed through the Service Quotas console" — file an AWS Support limit-increase case specifying endpoint/region/model/quota.
- [LIVE] `aws service-quotas list-service-quotas --service-code bedrock ... | grep mantle` → 16 matches; 8 quotas listed with codes/values, all `Adjustable=True`:
  - `L-54814DC6` input TPM Claude Opus 4.7 = 20,000,000; `L-15CD18AC` output TPM Claude Opus 4.7 = 4,000,000
  - `L-8528F119` input TPM Claude Opus 4.8 = 20,000,000; `L-37491D63` output TPM Claude Opus 4.8 = 4,000,000
  - `L-C593EA7C` input TPM GPT-5.4 = 1,000,000; `L-08036ECB` output TPM GPT-5.4 = 200,000
  - `L-2555C05B` input TPM GPT-5.5 = 500,000; `L-8A643E07` output TPM GPT-5.5 = 100,000
- Docs note only models in the published table (currently Claude Opus 4.7 in docs; our account also shows Opus 4.8 / GPT-5.4 / GPT-5.5) have exposed quotas; other mantle models are governed by internal capacity only.
- Verdict for us: real, adjustable, **account-wide per-model** hard backstop. Not per-user/per-team — the coarse outer wall only.

### 5. AgentCore Gateway native features

**5a. Policy engine (Cedar).** [DOC] https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/policy-core-concepts.html, policy-conditions.html, policy-authorization-flow.html, policy-test-a-policy.html, policy-limitations-section.html (all retrieved 2026-07-14):
- Principals: `AgentCore::OAuthUser` (from JWT `sub`; **all JWT claims become Cedar tags** — `principal.getTag("scope") like "*refund:write*"`, `principal.getTag("username") == ...`) or `AgentCore::IamEntity` (IAM ARN in `principal.id`, no tags). Our CUSTOM_JWT gateway ⇒ OAuthUser with Cognito claims.
- Request shape: principal + action + resource (gateway ARN) + `context.input` = the tool-call arguments. Conditions: `when/unless`, plus `when guardrails {...}` (conditions over guardrail outputs). `context.output` exists (output-side conditions) but "Mixing `context.input.` and `context.output.` in a single invocation is rejected."
- **Cedar has NO usage/quota state.** The documented evaluation context is exclusively identity claims, action, resource, and request (or guardrail/output) attributes. Nothing in the docs exposes counters, budgets, token tallies, or time-window aggregates to Cedar. Cumulative "user X has spent Y tokens today" enforcement is NOT expressible natively. (Negative finding; grounded in the pages above.)
- Enforcement modes: engine-level `mode` = `ENFORCE` (default) | `LOG_ONLY` set in `policyEngineConfiguration` on CreateGateway/UpdateGateway; per-policy `enforcementMode` = `ACTIVE` | `LOG_ONLY`; engine-level LOG_ONLY overrides everything (decisions computed + logged, never enforced). [DOC] policy-test-a-policy.html. [MODEL] `CreateGatewayRequest` members include `policyEngineConfiguration` and `interceptorConfigurations` (local service model, CLI 2.35.22).
- Limits: 10KB/policy, 200KB total/resource, 400KB Cedar schema/engine, 1000 policies/engine, 1000 engines/account. [DOC] policy-limitations-section.html.
- Cedar-for-INFERENCE-gateways specifics (what the action space looks like for `/inference` traffic, e.g. per-model actions): **not documented** anywhere I could find — all doc examples are MCP tool actions (`Target___tool_name`). See UNVERIFIED.

**5b. "Token limit policies" — REFERENCED IN DOCS, NOT PRESENT IN THE API (as of today).**
- [DOC] https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-target-inference-connector.html (retrieved 2026-07-14), "Response stream limits": "**AgentCore Gateway does not enforce a service-level maximum on response stream duration or response size. If you do not configure a token limit policy on your gateway target, each request can generate an unbounded streaming response.**" — and it names exactly our risks: gateway resource exhaustion, "Cost amplification on shared credentials — All users that route through the same target share one set of provider credentials," noisy-neighbor. It says "configure a token limit policy on your gateway targets. For more information, see Gateway policies."
- BUT: the "Gateway policies" link (`gateway-policies.html`) **redirects to the AgentCore overview page** (no such page); `gateway-token-limit-policies.html` also redirects to the overview (fetched both, retrieved 2026-07-14). [DOC-negative]
- [MODEL] `grep -c 'tokenLimit\|TokenLimit' .../bedrock-agentcore-control/2023-06-05/service-2.json` → **0**. `InferenceOperationConfiguration` = {path, providerPath, models}; `ModelEntry` = {model} only; no token-limit shape exists anywhere in the control-plane model. The inference **provider** target page's intro sentence claims you can "set per-model token limits" via provider config, but the documented/actual schema has no such field. [DOC] https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-target-inference-provider.html (retrieved 2026-07-14).
- Conclusion: **token limit policies are announced/telegraphed but not shippped on the public API surface as of 2026-07-14** (or ship via an undocumented channel). Do not design against them; do watch for them.

**5c. Gateway metrics + vended logs.**
- [LIVE] `AWS/Bedrock-AgentCore` for our gateways: `Invocations`, `Latency`, `Throttles`, `SystemErrors`, `InboundAuthorizationSuccess/Failure` per `Resource` = gateway ARN (probe on `uni-agent-gw-m*********`). **No token or per-user dimensions at the gateway.**
- Vended logs: gateway supports log delivery (CloudWatch Logs / S3 / Firehose) via `put-delivery-source` with `logType="APPLICATION_LOGS"` and `logType="TRACES"` (X-Ray) — default group `/aws/vendedlogs/bedrock-agentcore/gateway/APPLICATION_LOGS/{gateway_id}`. Logged: request start/completion, target config errors, authz failures, bad params, and **request and response bodies** for MCP operations, with `trace_id`/`span_id` correlation. [DOC] https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/observability-gateway-metrics.html + observability-configure.html (retrieved 2026-07-14).
- **USAGE_LOGS** is a documented log type for AgentCore **Runtime** observability (CDK `LogType.USAGE_LOGS` alongside `APPLICATION_LOGS`); the gateway docs describe only APPLICATION_LOGS + TRACES for gateway resources — no USAGE_LOGS delivery source documented for Gateway. [DOC] https://docs.aws.amazon.com/cdk/api/v2/python/aws_cdk.aws_bedrockagentcore/LogType.html (retrieved 2026-07-14). (Whether gateway vended APPLICATION_LOGS include *inference* — not just MCP — request/response bodies is undocumented; see UNVERIFIED.)

**5d. Interceptors (what the docs say).** [DOC] https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-interceptors-types.html (retrieved 2026-07-14):
- REQUEST runs before target, RESPONSE before replying. **Inference targets use the HTTP interceptor payload** ("HTTP targets (AgentCore Runtime and passthrough) and inference targets all use this `http` payload structure"); bodies are base64 strings; `headers` passed only with `passRequestHeaders:true`; REQUEST interceptor can return `transformedGatewayRequest` (headers+body — i.e., **can inject/rewrite outbound headers and body**) or short-circuit with `transformedGatewayResponse` (then RESPONSE interceptor does not run).
- **CRITICAL NEGATIVE:** "HTTP targets support both REQUEST and RESPONSE interceptors **in buffered mode**, in which the gateway buffers the full response before invoking the response interceptor. **Interceptors are not yet supported in streaming mode.**" The per-event streaming RESPONSE-interceptor contract (`isStreamingResponse`, invoked once per eligible event) is documented **for MCP targets only**. ⇒ On our streaming SSE inference lanes, a RESPONSE interceptor cannot observe/count output tokens today; only the REQUEST side is actionable (which matches our live setup: REQUEST interceptor fires on every call incl. /v1/models).
- Streaming passthrough: "the gateway passes through the SSE stream from the provider without transformation." [DOC] gateway-target-inference-connector.html.

**5e. Inference target routing (context).** Model-based routing on the `model` body field; `{targetName}/{modelId}` qualified routing; collision → prefer Bedrock target; connector `bedrock-mantle` auto-handles ops/paths/prefix-stripping; outbound auth `GATEWAY_IAM_ROLE` (SigV4) for Bedrock. `/v1/models` returns target-prefixed IDs. [DOC] gateway-target-inference-connector.html (retrieved 2026-07-14). [LIVE] `get-gateway` on `uni-agent-gw-m*********` → `authorizerType: CUSTOM_JWT`, `exceptionLevel: DEBUG`.

## Negative findings (record-of-absence, all grounded above)

- Application inference profiles: **not usable** through bedrock-mantle or the gateway inference connector (AWS says use Projects).
- Model invocation logging: **does not capture** mantle traffic (explicit doc statement).
- Per-request metadata tagging (billing): **not available** on mantle (explicit doc statement).
- IAM principal attribution (per-caller billing): **not yet** on mantle ("coming soon").
- CloudTrail: no token counts; inference events cost extra (data events).
- Gateway: **no native usage plans, rate limits, per-user quotas, or token-limit API fields**; no RPM/TPM feature on inference targets in the control plane today.
- Cedar policy: **cannot reference usage/quota state** — static identity claims + request context only; no counters.
- RESPONSE interceptors: **do not run in streaming mode for HTTP/inference targets** — no gateway-side output-token counting on our SSE traffic today.
- `AWS/BedrockMantle` has **no per-user dimension** — Project is the finest native slice; everything today lands in `Project="default"`.
- mantle quotas: per-account per-model per-region only; no per-user granularity; increases via Support case only.
- Budget Actions: not available for DAILY budget periods; 8–24h reaction latency class.

## Decision-relevant synthesis (for 02-DESIGN)

- The native building blocks that DO reach our path: **Projects** (per-team/app attribution: metrics dimension + billed-dollar tags in CE/CUR 2.0 + IAM-scopeable resource + Responses-state isolation), **AWS/BedrockMantle metrics** (near-real-time token telemetry incl. per-request datums at Project+Model), **mantle TPM quotas** (account backstop), **CloudTrail data events** (audit incl. verbatim `metadata`), **Cedar LOG_ONLY/ENFORCE** (identity/model allow-listing once inference action space is confirmed), **REQUEST interceptor** (per-request identity extraction, header/body rewrite — e.g., inject `OpenAI-Project`, clamp `max_tokens`, deny over-budget users via short-circuit 429), **Budgets Actions/CAD** (slow finance guardrail).
- The blocks that DON'T: AIPs, invocation logging, per-request billing metadata, IAM principal attribution (yet), Cedar usage state, streaming RESPONSE interceptors, any native token-limit/usage-plan API.
- Net: **fast-loop per-user metering/enforcement must be built** (REQUEST-interceptor + own ledger, with usage fed from AWS/BedrockMantle metrics and/or provider-reported usage captured by our pipe lane), while Projects + quotas + Budgets provide the native attribution and backstop layers. Projects-per-team (≤1000) via injected header is the most promising native upgrade — pending Spike #1.
